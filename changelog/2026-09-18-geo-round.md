## Why

The conversion fix set (`8ab3358`) fixed what Google sees. This round fixes what **answer engines**
see. A geo-optimizer 4.18.1 audit of production on 2026-09-18 scored the homepage **50/100
("foundation")** and the keratin post **61/100**. The gaps it named that were both standard and
truthful for this business:

- No `/llms.txt`, so an assistant crawling the site had no compact statement of who Melissa is,
  what she charges, or when she is open.
- No `WebSite` node, so the site had a business entity but no site entity to hang it off.
- The homepage FAQ existed as **microdata only**. Most LLM pipelines parse JSON-LD and ignore
  microdata, so those two answers were invisible to them.
- No feed, so there was no machine-readable index of the 7 blog posts.
- The keratin post opened with a quick-answer box but never defined what a keratin treatment *is*.
  Extractive models look for a definition sentence near the H1 to anchor a topic.

Deliberately skipped as non-standard or untruthful here: `/ai/*.json`, `/.well-known/ai.txt`,
WebMCP attributes, Wikipedia/Wikidata `sameAs` (none exist), and the keyword-density note.

## What changed

### G1 — `public/llms.txt` (Lead-written, pre-existing)
Hand-written, not generated from the sitemap. 54 lines: positioning, address, phone, hours, the
full price list, the 7 posts and the location pages. Every link verified to resolve to a real built
page; no link to the retired bare `/keratin/` URL.

### G2 — `WebSite` JSON-LD + RSS discovery link
`src/layouts/Layout.astro` gained a `WebSite` node (`@id` `…/#website`, `inLanguage` `en-NZ`,
`alternateName` "Hair By Melissa A" — the Google Business Profile name) whose `publisher` points at
the HairSalon block's **existing** `@id`, `…/#business`.

> Deviation from the plan's literal text, recorded on purpose: §10 says to give the salon block an
> `@id` of `…/#salon` "if it lacks one". It did not lack one — it already had `…/#business`. Adding
> `#salon` would have created a second identifier for one entity, so the existing `#business` was
> reused. Verified non-dangling: both the declaration and the reference are present in `dist`.

Also added `<link rel="alternate" type="application/rss+xml" href="/rss.xml">` to `<head>`.

### G3 — RSS feed
`npm i @astrojs/rss` (4.0.19). New `src/data/blogPosts.ts` mirrors the `pageTitle` /
`pageDescription` / `slug` / `publishDate` / `modifiedDate` constants of the 7 blog pages (they are
plain `.astro` pages, not a content collection, so there is nothing to derive them from). New
`src/pages/rss.xml.ts` renders `/rss.xml`, newest-first, `<language>en-nz</language>`.

`blogPosts.ts` is a hand-mirrored copy and **will drift** if a post's constants change. Its header
comment says so. Converting the blog to a content collection (plan §6, "structural") removes this
duplication permanently.

### G4 — Homepage FAQPage JSON-LD
`src/pages/index.astro`: the two hard-coded "Voice Search FAQ" questions moved into one `homeFaqs`
array that now feeds **both** the visible microdata block and a new single `FAQPage` JSON-LD block.
Answer text unchanged, character for character, including the US spelling "specializes" and the
`$180 / $230 / $50` figures. No second visible accordion, no client-side JS.

### G5 — Keratin post definition opening
`src/pages/blog/keratin-aftercare.astro`: a definition paragraph inserted verbatim as the first body
paragraph, above the quick-answer box. `dateModified` was already `2026-09-18`. (An orphaned comment
calling the quick-answer box "first content block after the H1" was corrected to match.)

SSRF guard (`geo_optimizer/utils/validators.py`, `_BLOCKED_HOSTNAMES` / `_is_ip_blocked`), which
rejects `localhost` and every loopback and private IP. There is no `--allow-local` flag, config key
or environment override. The guard was left intact on purpose rather than patched. Since the
"before" numbers were measured against production, the comparable "after" run is also a production
run, **after this commit deploys**:

## Known issues left open

- **`public/sitemap.xml` is a stale hand-written sitemap (16 KB, 443 `<loc>` entries) that still
  lists `/404`.** Plan §8b assigned its deletion to the previous round's QA-2; it was never done. It
  is not referenced by `robots.txt` (which points only at `sitemap-index.xml` and
  `sitemap-images.xml`) and not linked from any page, so it is dead weight rather than an active
  crawl signal — the served sitemap, `sitemap-0.xml`, is correct at 38 URLs with no `/404` and no
  `/rss.xml`. **Not fixed here on purpose:** deleting it makes `/sitemap.xml` return 404, which is a
  URL change requiring 301s in `public/netlify.toml` and `public/_redirects`, and that belongs in the
  sitemap-hygiene change set, not in a GEO commit. Recommend: delete the file and 301
  `/sitemap.xml` → `/sitemap-index.xml` as its own commit.
- `src/data/blogPosts.ts` duplicates each post's constants by hand and can drift. Resolved by the
  content-collections refactor already deferred in plan §6.
- The homepage FAQ is still only two questions, both written for voice search. Expanding it is a
  content task, not a schema one.
